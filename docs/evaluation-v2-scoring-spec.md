# Evaluation V2 — Scoring Specification (E1.1)

สถานะ: **ร่างสำหรับอนุมัติและตรวจสอบเกณฑ์**; ยังไม่ใช่กติกาที่เปิดใช้ในระบบ

วันที่ตรวจแหล่งอ้างอิง: 17 ตุลาคม 2026

ขอบเขต: Backend / Evaluation Logic / External API Integration ในอนาคตเท่านั้น ไม่มีการเปลี่ยน Source Code ใน E1.1

## 1. ความหมายและขอบเขต

คะแนน 0–100 เป็น **ดัชนีความเหมาะสมของแผนที่โครงการนิยาม** ไม่ใช่ความน่าจะเป็นที่จะปลอดภัย ไม่รับรองว่าเส้นทางหรืออุทยานเปิดจริง และไม่ใช้แทนประกาศหน่วยงานหรือการตัดสินใจของผู้เดินทาง น้ำหนักและการแปลงข้อมูลอุตุนิยมวิทยาเป็น `L` เป็นแบบจำลองของโครงการ มิใช่สูตรที่กรมอุตุนิยมวิทยา, Open-Meteo, OSRM หรือ ISO รับรอง [R1–R8](evaluation-v2-references.md)

### Input หลักจากผู้ใช้

1. อุทยานปลายทาง (park ID ที่ระบุได้แน่นอน)
2. ต้นทาง (ข้อความหรือจุดที่ผู้ใช้เลือก; Live ต้องจับคู่พิกัดที่ตรวจสอบได้)
3. วันที่ออกเดินทาง
4. เวลาออกเดินทางพร้อมเขตเวลา
5. พาหนะ

จำนวนคน, เวลาที่ต้องการเที่ยว, เวลาเผื่อ, สภาพอากาศ และระยะเวลาเดินทาง **ไม่ใช่ input บังคับ** ของ V2 หากข้อมูลเสริมมีอยู่ ให้ใช้เฉพาะงานที่ระบุ provenance ได้ ห้ามเติมค่าเงียบ ๆ ให้คะแนนครบ

### ข้อมูลระบบและ Output

ข้อมูลระบบ: พิกัดต้นทาง/จุดเข้าอุทยานและสถานะการตรวจสอบ, route profile/geometry/duration/waypoint snap, พยากรณ์ตามพิกัดและเวลา, ชั่วโมงเข้าชมพร้อมแหล่งและวันที่มีผล, เวลาพระอาทิตย์ตกที่คำนวณจากวันและพิกัดจริง, ประกาศที่ตรวจสอบได้ (ถ้ามี) ข้อมูลพยากรณ์เป็น forecast ไม่ใช่ observation หรือคำยืนยันสถานะพื้นที่

ผลลัพธ์: `evaluationStatus` (`COMPLETE`/`INCOMPLETE`), `W,WR,WP,D,T,A` ซึ่งอาจเป็น `UNKNOWN`, `S`/level เฉพาะ `COMPLETE`, เหตุผลและ coverage ของข้อมูลที่หาย, `warningSeverity`, constraints, `canProceed` (`TRUE`/`FALSE`/`UNKNOWN`), `formulaVersion`, เวลาและ provenance ของทุกแหล่ง ค่าที่เป็น `UNKNOWN` **ไม่ใช่ศูนย์**

## 2. Weather (W)

### 2.1 ตัวแปรและความสอดคล้องของเวลา

ใช้ Open-Meteo hourly `precipitation` (ผลรวม **ชั่วโมงก่อนหน้า**, mm ต่อหนึ่งชั่วโมง), `wind_gusts_10m` (ค่าสูงสุด **ชั่วโมงก่อนหน้า**, km/h), และ `weather_code` (รหัส ณ ชั่วโมงที่ระบุ) ชื่อหน่วย `mm/hour` ในตารางด้านล่างหมายถึงปริมาณในหนึ่งช่องเวลาหนึ่งชั่วโมง ไม่ใช่อัตราฝน ณ ทุกนาทีของชั่วโมง ค่า `null`, timestamp ผิด, หน่วยผิด, หรือรหัสที่ไม่รองรับเป็น `UNKNOWN` [R3](evaluation-v2-references.md)

สำหรับช่วง `[h,h+1)` ให้ใช้ precipitation/gust record ที่ปิดช่วงนั้น ณ `h+1`; ใช้ weather code ที่เวลาใกล้เหตุการณ์ที่สุดและบันทึกเวลาที่เลือกไว้ ห้ามนำฝนสะสม 24 ชั่วโมงของ TMD มาเทียบกับตัวเลขรายชั่วโมงโดยตรง และห้ามอ้างว่าฝนรายชั่วโมงของแบบจำลองเท่ากับความเข้มฝนช่วงสั้นที่เครื่องตรวจวัด [R1,R2,R3](evaluation-v2-references.md) **โค้ด Evaluation ปัจจุบันดึง Open-Meteo แบบ `daily` (`precipitation_sum`, `wind_speed_10m_max`) และ OSRM snapshot มี geometry/duration รวมแต่ไม่ได้ขอ segment annotations** จึงยังผลิต `L_i`, `WR`, `WP` ตามข้อนี้ไม่ได้ ต้องเพิ่ม infrastructure เฉพาะ V2 และตรวจข้อมูลจริงก่อนคิดคะแนน ห้ามนำค่ารายวันของ V1 มาแปลงเป็นรายชั่วโมง [R10](evaluation-v2-references.md)

### 2.2 ระดับผลกระทบต่อแผน `L = 0,1,2,3`

ตารางต่อไปนี้เป็น **candidate rubric** ที่ต้องผ่านการทบทวนตาม [Validation Plan](evaluation-v2-validation-plan.md) ก่อนเปิดใช้ `L` เป็นระดับผลกระทบต่อแผนตามโครงการ ไม่ใช่ชื่อชั้นมาตรฐานฝน/ลม

| L | ฝน `p` ในช่อง 1 ชั่วโมง | ลมกระโชก `g` สูงสุดในช่อง 1 ชั่วโมง | รหัสสภาพอากาศขั้นต่ำ | ที่มาของตัวเลข |
|---|---|---|---|---|
| 0 | `p = 0` | `0 ≤ g < 56 km/h` | `0–3` | ขอบ `56` เป็นค่าตั้งต้นของโครงการ; **ไม่มีเกณฑ์ไทยรองรับ** |
| 1 | `0 < p < 2.5 mm` | `56 ≤ g < 72 km/h` | `51,53,55,61,80` | `2.5` เป็นจุดแบ่ง **ทดลองของโครงการ** สำหรับผลรวมพยากรณ์ 1 ชั่วโมง |
| 2 | `2.5 ≤ p < 10 mm` | `72 ≤ g < 93 km/h` | `63,81` | `10` เป็นจุดแบ่ง **ทดลองของโครงการ** สำหรับผลรวมพยากรณ์ 1 ชั่วโมง |
| 3 | `p ≥ 10 mm` | `g ≥ 93 km/h` | `65,82,95,96,97,99` | การแปลงปริมาณ/รหัสเป็นระดับผลกระทบ **โครงการกำหนดเอง** |

ตัวเลขลม `56` เป็นค่าตั้งต้นของโครงการ ส่วน `72/93` เป็นการปัดค่า 45/58 mph และยืมบริบทเกณฑ์เตือนของสำนักงาน NWS ในสหรัฐฯ มาเป็น **จุดตั้งต้นในการทดลอง** ไม่ใช่เกณฑ์เตือนภัยอุทยานไทยหรือหลักฐานว่าลมต่ำกว่า 56 km/h ปลอดภัย [R5](evaluation-v2-references.md) ตัวเลขฝน `2.5/10` **ไม่ถือเป็นการนำเกณฑ์ WMO มาใช้โดยตรงหรือการดัดแปลงที่ได้รับการตรวจสอบแล้ว**: WMO จัดชั้น *ความเข้มที่วัดช่วงสั้น* ขณะที่ `p` เป็นผลรวมจากแบบจำลองตลอดชั่วโมง ฝน 10 mm อาจตกกระจายในหนึ่งชั่วโมงหรือกระจุกในไม่กี่นาที จึงมีผลต่อสภาพจริงต่างกัน ตัวเลขดังกล่าวเป็นเพียง candidate ที่ต้องเทียบกับตัวอย่างฝนพยากรณ์/ตรวจวัดในไทยและให้ผู้เชี่ยวชาญอนุมัติ [R2,R3](evaluation-v2-references.md) `p=0` ก็ไม่ยืนยันว่าตลอดชั่วโมงไม่มีฝนเฉพาะจุด

`L_i = max(L_rain, L_gust, L_code)` เมื่อ **ทั้งสามข้อมูลอยู่ครบและเทียบช่วงเวลาได้** การใช้ `max` กันการหักคะแนนซ้ำจากพายุที่ปรากฏทั้งฝนและ weather code พร้อมเก็บเหตุที่ทำให้ได้ `L` สูงสุดทั้งหมดไว้ หากตัวแปรใดขาด ให้ `L_i=UNKNOWN`; ข้อยกเว้นคือยังออก **warning แยกต่างหาก** ได้จากหลักฐานรุนแรงที่ทราบอยู่แล้ว แต่ไม่เติมคะแนนที่หาย ถ้า weather code บอกฝนหนักแต่ปริมาณฝนต่ำ ให้คงระดับสูงกว่าและบันทึก `DATA_CONFLICT` เพื่อทบทวน

รหัส `45,48` (หมอก) และรหัสหิมะ/ฝนเยือกแข็ง (`66,67,71–77,85,86`) ยังไม่มี rubric ที่เหมาะกับพื้นที่นี้: ให้ `L=UNKNOWN` และแสดงปรากฏการณ์จริง; หากมีการเตือนรุนแรงให้เปิด warning ร่วมด้วย **ห้ามตีความเป็นอากาศดี** รหัสที่ provider ไม่รู้จักก็เป็น `UNKNOWN` [R3](evaluation-v2-references.md)

### 2.3 Severe Weather Warning

แยก `forecastHazardFlag` ออกจาก **ประกาศเตือนภัยทางการ** อย่างชัดเจน:

- Candidate flag จากแบบจำลอง: hourly code `95,96,97,99` หมายถึงพยากรณ์ฟ้าคะนองตามรหัส ไม่ได้ยืนยันว่าพายุถึงเกณฑ์รุนแรง; `p ≥ 25.1 mm` หรือ `≥ 50.1 mm` ในช่องหนึ่งชั่วโมงเป็นการเทียบค่า *พยากรณ์* กับชั้นฝนหนัก/หนักมาก **1 ชั่วโมง** ของ TMD ไม่ใช่ประกาศ TMD; `g ≥ 93 km/h` เป็นเกณฑ์ทดลองจากบริบท NWS สหรัฐฯ ไม่ใช่เกณฑ์ไทย [R1,R3,R5](evaluation-v2-references.md) เก็บ trigger, หน่วย, ช่วงเวลา, พิกัด, provider/model time และระดับความไม่แน่นอน ถ้าค่า `p=25.0` ห้ามเรียกว่าฝนหนักตามเกณฑ์ 25.1 ของ TMD แม้ `L_rain=3` ตามเกณฑ์ทดลอง
- `officialWarning` ต้องเป็นประกาศจากหน่วยงานที่ตรวจสอบ URL/เวลา/พื้นที่ที่ครอบคลุมได้ แสดงข้อความและความมีผลแยกจาก forecast flag; ไม่มีประกาศในระบบ **ไม่เท่ากับไม่มีประกาศจริง** คำว่า `BLOCKING` หรือ `canProceed=FALSE` ต้องมีหลักฐานข้อห้าม/การปิดตรงสถานที่และวันเดินทาง

ห้ามใช้ flag หรือประกาศเพิ่ม ETA โดยไม่มีข้อมูล route/traffic รองรับ ห้ามอนุมานว่าถนนหรืออุทยานปิด และห้ามให้คะแนน `L=3` เพียงอย่างเดียวกลบเหตุเตือนภัยหรือแปลงเป็นคำสั่งห้ามเดินทาง

### 2.4 WR และ WP

ให้แบ่งเวลาเดินทาง `[DepartureAt, ArrivalAt)` ออกเป็นช่วง `i` ที่ไม่ซ้อนกันตามช่องพยากรณ์และเส้นทาง กำหนด `dt_i` เป็นระยะเวลาที่อยู่ในช่วงนั้น (นาที), `p_i` เป็นจุดบน route geometry ที่คาดว่าผ่านกลางช่วง, `L_i` จาก forecast ของพิกัด/ช่วงนั้น หากมี OSRM annotation รายช่วงที่จับกับ geometry ได้ให้ใช้เวลารายช่วง หากมีเพียง geometry กับ duration รวม ให้การกระจายเวลาโดยระยะทางเป็นเพียง *estimation method* ที่ต้องบันทึกและตรวจสอบความคลาดเคลื่อน ห้ามอ้างว่าเป็นเวลา provider ยืนยันรายจุด [R4](evaluation-v2-references.md)

`W_i = 100 × (1 - L_i/3)`

`WR = SUM(dt_i × W_i) / SUM(dt_i)` เมื่อทุกช่วงมี `L_i` และ `SUM(dt_i) > 0`

ต้องมี forecast ต้นทาง, จุดระหว่างทางตามเส้น และจุดก่อนถึงอุทยาน ไม่จำเป็นต้องยิงหนึ่ง API call ต่อจุด; วาง sampling/caching ตามขีดจำกัด provider ถ้าข้อมูลช่วงใดไม่มีหรือ geometry ไม่พอให้ `WR=UNKNOWN` พร้อมรายการช่วงที่หาย ไม่ normalize ด้วยช่วงที่เหลือแล้วเรียกว่า WR ครบ

`WP` คือ `W_arrival`: ใช้ forecast **ช่องหนึ่งชั่วโมงที่ครอบคลุม ArrivalAt** ณ จุดอ้างอิงอุทยาน และ weather code ที่ใกล้ ArrivalAt ที่สุด นี่คือ *สภาพอากาศคาดการณ์ตอนถึง* ไม่ใช่คะแนนอากาศตลอดการเที่ยว จึงไม่สมมติชั่วโมงเที่ยวที่ผู้ใช้ไม่ได้ให้ หากพิกัดปลายทางยังต้องตรวจทานหรือช่องพยากรณ์ไม่ครอบคลุม ให้ `WP=UNKNOWN` ไม่ใช้ forecast รายวันแทนโดยปริยาย

`W = 0.40WR + 0.60WP` เมื่อทั้งสองครบ น้ำหนัก 40/60 เป็น **น้ำหนักทดลองของโครงการ**; sensitivity ต้องทดสอบ 30/70, 50/50 และ 60/40 [R6](evaluation-v2-references.md)

## 3. Duration (D): ภาระด้านเวลาเดินทาง

ใช้ `d = RouteDuration / 60` นาทีจาก route profile ที่ **รองรับพาหนะที่เลือกจริง** ไม่ใช้ฝน/พายุเพิ่ม ETA, ไม่คูณเวลาของรถยนต์เพื่อแทนมอเตอร์ไซค์หรือขนส่งสาธารณะ และไม่ใช้ระยะเส้นตรงแทนเวลาเดินทาง หากไม่มี route ที่เหมาะสมหรือ provider ล้มเหลว ให้ `D=UNKNOWN` [R4,R7](evaluation-v2-references.md)

**ข้อเสนอแนะนำ: linear normalization** `D_linear(d) = 100 × CLAMP(1 − d/600, 0, 1)` สำหรับ `d ≥ 0`; 0 นาที→100, 300 นาที→50, ตั้งแต่ 600 นาที→0 ขอบ 600 นาทีอ้างอิงเพียง breakpoint ท้ายของ **V1 ในโครงการ** ไม่ได้มาจากมาตรฐานแพทย์หรือเกณฑ์อุบัติเหตุ คะแนน 0 หมายถึงภาระเวลาสูงตามสเกลนี้ ไม่ได้หมายถึงเกิดอุบัติเหตุแน่นอน

**ตัวเลือก piecewise เพื่อเปรียบเทียบ:** interpolate เชิงเส้นระหว่างจุด `(0,100),(90,95),(180,80),(300,60),(420,40),(600,0)` และคง 0 เมื่อมากกว่า 600 นาที จุด 90/180/300/420/600 สืบจากจุดแบ่งเดิมของ V1; คะแนนปลายแต่ละช่วงเป็นข้อเสนอของโครงการ ไม่มีงานวิจัยยืนยันว่าค่าเหล่านี้เหมาะกับทริปอุทยาน

| วิธี | ข้อดี | ข้อจำกัด |
|---|---|---|
| Linear | อธิบายและทดสอบง่าย, monotonic, พารามิเตอร์เดียว | ลดคะแนนเท่ากันทุกนาที; จุด 600 เป็นสมมติฐาน |
| Piecewise | ปรับความไวต่อช่วงเดินทางได้และเทียบกับ V1 ง่าย | จุดหักมากขึ้นและเปิดช่องให้ tune ตามความรู้สึก; ต้องตรวจสอบทุก breakpoint |

**คำแนะนำ:** ใช้ linear เป็น candidate หลักเพื่อทดสอบความไวของ 480/600/720 นาที และนำผลผู้เชี่ยวชาญ/ตัวอย่างทริปจริงมาตัดสินก่อนเปิดใช้ ไม่อ้างว่าทั้งสองวิธีคือแบบจำลองความเสี่ยงอุบัติเหตุ งานด้าน transport appraisal รองรับเพียงการนับเวลาเป็นองค์ประกอบหนึ่งของภาระการเดินทาง ไม่ได้กำหนดสเกล 0–100 ของโครงการ [R7](evaluation-v2-references.md)

## 4. Time Suitability (T)

คำนวณ timestamp ในเขตเวลาอุทยาน: `ArrivalAt = DepartureAt + RouteDuration` โดยไม่เพิ่ม ETA จากฝน/ลม สำหรับ **ช่วงเข้าชมช่วงเดียวที่ตรวจสอบได้** `[OpeningAt,ClosingAt)` และ `ClosingAt > OpeningAt`:

`OpeningWindow = ClosingAt − OpeningAt`

`RemainingVisitTime = MAX(0, ClosingAt − MAX(ArrivalAt,OpeningAt))`

`T = 100 × CLAMP(RemainingVisitTime / OpeningWindow, 0, 1)`

**หลายช่วงเข้าชม:** สร้างชุดช่วงที่ไม่ซ้อนกันของ *service day* เดียว `I_d = {[open_j,close_j)}` หลังตรวจตารางที่มีผลต่อวันที่ถึงและ timezone อุทยาน; ช่วงเปิดข้ามคืนผูกกับวันที่เริ่มเปิด แม้เวลาปิดอยู่วันถัดไป `OpeningWindow_d = SUM_j(close_j-open_j)` และ `RemainingVisitTime_d = SUM_j max(0, close_j-max(ArrivalAt,open_j))` (ค่าส่วนที่เกินช่วงเป็น 0) จากนั้น `T=100×CLAMP(RemainingVisitTime_d/OpeningWindow_d,0,1)` สูตรช่วงเดียวด้านบนเป็นกรณีพิเศษ **ไม่รวมเวลาพักปิดกลางวันในตัวส่วนหรือเวลาที่เหลือ** ช่วงที่ชนกันให้รวมก่อนนับ; ช่วงทับกัน/ขัดกันที่ไม่ทราบความหมายให้ `T=UNKNOWN` จนตรวจข้อมูลต้นทาง

เลือก service day อย่างกำหนดแน่นอน: ถ้า `ArrivalAt` อยู่ในช่วงเปิดข้ามคืนที่เริ่ม **วันก่อน** ให้ใช้ service day วันก่อนนั้น; มิฉะนั้นใช้วันที่ตามปฏิทิน ณ จุดหมายของ `ArrivalAt` ห้ามเลือก service day ถัดไปเพียงเพื่อเพิ่มคะแนน เมื่อถึงก่อนช่วงแรกของวันให้ `T=100` แต่แจ้งเวลารอ; เมื่อถึงในช่วงพักให้คิดเฉพาะช่วงที่ยังเหลือ; ถึงตรง/หลังปิดช่วงสุดท้ายให้ `T=0` ของ service day นั้น แม้พรุ่งนี้เปิดอีก เดินทางข้ามวันต้องใช้วันที่ถึงจริง ไม่ใช้ `HH:mm` ของวันออกเดินทาง กรณีมีสอง service day ซ้อนครอบคลุม ArrivalAt หรือระบุวันเริ่มรอบไม่ได้ให้ `T=UNKNOWN` และรายงานความกำกวม **ข้อยกเว้นจากสูตรหาร:** ตารางที่ยืนยันชัดว่าวันนั้นไม่มีรอบเปิดให้ `T=0` พร้อมเหตุ; หากได้ `OpeningWindow=0` จากข้อมูลช่วงเวลาที่เสีย/ไม่ครบ ให้ `T=UNKNOWN` ตารางหาย/เก่า/ขัดกันก็ให้ `T=UNKNOWN` **T=0 ไม่ใช่คำตัดสินว่าห้ามเข้า** และเวลาเปิดทั่วไปในฐานข้อมูลไม่ยืนยันสถานะเปิดสดหรือข้อยกเว้นรายวัน

Sunset ใช้ค่าที่คำนวณจากวันที่และพิกัดจริงใน Live เพื่อ **เตือนเรื่องแสงสว่าง** เท่านั้น หากไม่มี sunset ให้เตือนว่าไม่มีข้อมูลนี้ ไม่ใช้ `18:30` หรือเวลา mock และไม่เปลี่ยน T โดยอัตโนมัติ เว้นแต่จะมีเกณฑ์กิจกรรมกลางวันที่ได้รับอนุมัติแยกต่างหาก `T` คือสัดส่วน **ช่วงเวลาเข้าชมที่เหลือ** ไม่ใช่เปอร์เซ็นต์ความปลอดภัย

## 5. Accessibility (A): หลักฐานการเข้าถึงฝั่งจุดหมาย

สูตรทดลอง `A = 100 × PassedVerifiedChecks / TotalApplicableChecks` ใช้ได้ **เมื่อทุก critical applicable check มี PASS/FAIL จากหลักฐานที่ตรวจสอบได้** และตัวส่วนมากกว่าศูนย์ `UNKNOWN` หรือ `NOT_APPLICABLE` ต้องมีเหตุผล; ห้ามลบ check ที่ตรวจไม่ได้ออกจากตัวส่วนเพื่อให้คะแนนสูงขึ้น กำหนดรายการที่ applicable จากพาหนะและจุดหมาย **ก่อน** ดูผล check เพื่อกันการเลือกตัวส่วนตามผลลัพธ์

**ขอบเขตไม่ซ้ำกับ D:** `D` ใช้ความยาวเวลาเดินทางจาก route ที่รองรับพาหนะ; route profile ที่ใช้ได้, `NoRoute`, geometry, snap distance และ provider failure เป็น *preconditions/diagnostics* ของ Routing/Timeline ไม่ใช่ check ที่ให้คะแนน A ซ้ำอีกครั้ง `A` ประเมินเฉพาะหลักฐานฝั่งจุดหมายว่าจุดอ้างอิงและกติกาการเข้าถึงตรงกับการเดินทางที่ถามหรือไม่ การมี OSRM route ไม่พิสูจน์ว่าเข้าเขตอุทยานได้จริง [R4,R9,R10](evaluation-v2-references.md)

| Check | หลักฐานที่ต้องมี | PASS / FAIL / UNKNOWN |
|---|---|---|
| A1 จุดหมายที่ใช้อ้างอิง | พิกัดทางเข้าหรือจุดรับผู้เดินทางที่ตรวจสอบกับแหล่งข้อมูลอุทยานได้ พร้อมวันตรวจ | PASS เมื่อยืนยันว่าพิกัดนั้นเป็นจุดรับจริง; FAIL เมื่อพิสูจน์ว่าผิดจุด; UNKNOWN เมื่อมีเพียงพิกัดอุทยานโดยประมาณ |
| A2 กติกาพาหนะ ณ จุดหมาย | ประกาศ/ข้อมูลผู้ดูแลพื้นที่ที่ตรงกับพาหนะ จุดเข้า และวันที่เดินทาง | PASS เมื่อมีหลักฐานว่าอนุญาตตามเงื่อนไข; FAIL เมื่อมีข้อห้ามตรงกรณี; UNKNOWN เมื่อไม่มีข้อมูลที่ยังมีผล |
| A3 ช่วงเข้าถึงสุดท้าย (เมื่อจำเป็น) | ข้อมูลจุดลง/จุดจอดและบริการต่อรถหรือช่วงเดินที่ครอบคลุมถึงจุดรับ พร้อมข้อจำกัด | PASS เมื่อมีหลักฐานเชื่อมครบ; FAIL เมื่อพิสูจน์ว่าขาด; UNKNOWN เมื่อไม่มีหลักฐาน; N/A เมื่อยืนยันได้ว่าไม่ต้องต่อ |

**รูปแบบที่ใช้ข้อมูลปัจจุบันได้ทันทีโดยไม่อ้างเกิน:** ส่ง `accessEvidenceStatus` แบบไม่เป็นคะแนน (`REFERENCE_RECORDED`, `REFERENCE_NEEDS_REVIEW`, `DESTINATION_ACCESS_UNVERIFIED`) พร้อม park ID, พิกัดอ้างอิงจาก DB, ผล audit พิกัด, ที่อยู่/คำอธิบายการเดินทางถ้ามีและแหล่งที่มา; แสดงแยก `routeDiagnostic` จาก OSRM [R9,R10](evaluation-v2-references.md) สถานะเหล่านี้บอกเพียงว่ามีข้อมูลอ้างอิงและต้องตรวจอะไรต่อ **ไม่ใช่ PASS ของ A1–A3 และไม่บอกว่าพาหนะเข้าได้** ข้อมูล fee ของยานพาหนะ, ที่อยู่หรือคำบรรยายการต่อรถอย่างเดียวไม่ใช่หลักฐานสิทธิหรือบริการที่ยังใช้ได้

โครงการยังไม่มีทะเบียนทางเข้าที่ตรวจสอบแล้วหรือหลักฐานพาหนะ/last mile ครบทุกแห่ง จึงให้ `A=UNKNOWN`, `S=null`, `INCOMPLETE` ใน V2 จนมีหลักฐานที่ต้องใช้ครบ ห้ามนำ route success หรือความครบของ metadata ไปทำ `A=100` หากต้องการเปลี่ยน A เป็น *data readiness* เพื่อให้คำนวณ S ได้ ต้องถือเป็น **การเปลี่ยนความหมายของปัจจัย** และอนุมัติสูตร/การตีความใหม่แยกต่างหาก

## 6. Overall score และกฎการตัดสินใจ

`S = 0.30W + 0.20D + 0.30T + 0.20A` ใช้เมื่อทุกตัวอยู่ใน `[0,100]` และ provenance ครบ น้ำหนักเป็น **ค่าทดลองโครงการ** [R6](evaluation-v2-references.md)

- `COMPLETE`: ทุก factor และส่วนประกอบที่จำเป็นมีค่าที่ตรวจสอบย้อนกลับได้; อาจมี `warning` หรือแม้แต่ verified blocking constraint ได้ เพราะความครบของการคำนวณแยกจากคำแนะนำให้เดินทาง
- `INCOMPLETE`: ขาด/เก่า/ขัดกัน/ไม่รองรับใน factor ใด; แสดงคะแนนย่อยที่ทราบแต่ `S=null` และ `level=null`; ไม่ renormalize น้ำหนัก, ไม่แทน unknown ด้วย 0 หรือค่าเฉลี่ย
- `canProceed=FALSE` เฉพาะข้อห้ามหรือการปิดที่มีหลักฐานทางการตรงสถานที่/เวลา; `UNKNOWN` เมื่อสถานะสำคัญยังยืนยันไม่ได้; `TRUE` ใช้ได้เมื่อ critical checks เรื่องการเข้าใช้พื้นที่/พาหนะที่กำหนดไว้ตรวจครบและผ่าน โดยยัง **ไม่ใช่การรับประกันความปลอดภัย** การมาถึงหลังเวลาท่องเที่ยวทั่วไปเป็น advisory เว้นแต่มีหลักฐานว่าเป็นข้อห้ามเข้า
- Severe weather warning แยกจากคะแนนและ level; ไม่ให้คะแนนสูงกลบคำเตือนและไม่แปลง warning เป็นข้อห้ามทางการโดยอัตโนมัติ
- คำนวณด้วยทศนิยมเต็มความละเอียด; clamp factor ที่ขอบ 0–100; ปัด `S` **ครั้งเดียว** เป็นจำนวนเต็มแบบ half-up เพื่อแสดงและบันทึก พร้อมเก็บค่าดิบที่ใช้ audit; ห้ามปัด WR/WP/คะแนนย่อยก่อนรวม
- ใช้ `formulaVersion` เช่น `evaluation-v2.0-candidate-1` และ `rubricVersion` แยกกัน เก็บ provider, request/forecast/model time, timezone, coordinates, route profile/duration/geometry identity, park hours source/effective date, check evidence IDs, thresholds, weights, warnings, missing reasons และ input fingerprint; ห้ามเก็บ secret หรือ raw ข้อมูลเกินจำเป็น
- V1 history, สูตร 35/25/20/20, ชื่อ `userProfileScore`, DTO และผล Manual เก่ายังคงแสดงเป็น V1; ไม่ migrate คะแนนเก่าให้กลายเป็น V2 และไม่เปิด V2 เป็นผลหลักจน persistence/consumer รองรับ UNKNOWN กับเวอร์ชัน

## 7. ตัวอย่างคำนวณ (ข้อมูลสมมติ ไม่ใช่คำแนะนำการเดินทางจริง)

สมมติ WR มีสองช่วง: 60 นาที `L=0`, 120 นาที `L=1` → `WR=(60×100+120×66.6667)/180=77.7778`; ช่องพยากรณ์ตอนถึง `L=1` → `WP=66.6667`; `W=0.4×77.7778+0.6×66.6667=71.1111` สมมติ route รองรับพาหนะและให้ `d=180` นาที ออก 08:00 ถึง 11:00 → `D_linear=100×(1−180/600)=70` เปิด 08:00–17:00 → `T=100×6/9=66.6667` **เพื่อแสดงคณิตศาสตร์เท่านั้น** สมมติว่ามีหลักฐาน A1–A3 ครบและผ่าน 3/3 → `A=100`; ได้ `S=0.30×71.1111+0.20×70+0.30×66.6667+0.20×100=75.3333` → แสดง `75` ตัวอย่างนี้ไม่ใช่ข้อมูลที่ระบบปัจจุบันยืนยันได้ และน้ำหนักทุกชุดยังเป็นค่าทดลอง

ถ้า A1 ยังไม่ยืนยันพิกัดทางเข้า ตัวอย่างเดียวกันต้องเป็น `A=UNKNOWN`, `S=null`, `INCOMPLETE` แม้ตัวเลขอื่นครบ

## 8. ประเด็นที่ยังต้องอนุมัติก่อนเปิด V2 Scoring

1. อนุมัติ/ปรับจุดแบ่ง hourly rain `2.5/10 mm` ที่โครงการตั้งเป็นตัวทดลอง (WMO ไม่รับรองการแปลงผลรวมพยากรณ์รายชั่วโมง), gust 56/72/93 km/h ที่ตั้ง/ดัดแปลงจาก NWS และ forecast flag เทียบชั้นฝน TMD พร้อมผลตรวจผู้เชี่ยวชาญในบริบทภาคเหนือ
2. อนุมัติฟังก์ชัน D, จุด 600 นาที และ sensitivity ของ threshold; ตัดสินพาหนะที่ provider รองรับจริง
3. ระบุ source of truth ของทางเข้าอุทยาน, เวลาเข้าชม **ทุกช่วง** ตามวันที่/service day, ข้อจำกัดพาหนะ และ last mile เพื่อให้ A/T `COMPLETE` ได้; ตรวจ 4 อุทยานที่พิกัดขัดกัน
4. อนุมัติวิธีประมาณ passage time จาก OSRM annotation/geometry, tolerance ของ forecast coverage/freshness และเพดานคำขอ provider
5. อนุมัติ semantics ของ `TRUE/FALSE/UNKNOWN`, forecast hazard flag เทียบกับประกาศทางการ, level ใหม่ และแนวทางเก็บ partial result ที่ไม่ทำลาย V1

ไม่มีหลักฐานที่ตรวจพบว่าค่าน้ำหนัก 30/20/30/20, 40/60, threshold เวลา 600 นาที, จุดแบ่งฝน 2.5/10 ของ *hourly forecast* หรือรายการ check A ได้รับการรับรองโดยมาตรฐานภายนอก แม้ตัวอย่างคำนวณได้คะแนนครบ ก็ไม่ใช่หลักฐานว่า production data ครบหรือคะแนนเหมาะกับการตัดสินใจจริง

### ข้อเสนอเริ่ม E2 เฉพาะ Infrastructure (ยังไม่เปลี่ยนคะแนน Production)

1. **Routing:** ตรวจ profile ที่ใช้งานจริง, geometry, snapped endpoints และทางเลือกขอ OSRM segment `annotations=duration,distance`; บันทึกความสามารถ/ข้อผิดพลาดพร้อม provenance โดยไม่แก้ route snapshot เดิมหรือ D ของ V1 ก่อนออกแบบ compatibility
2. **Timeline:** คำนวณ timestamp พร้อม timezone และ service day, normalize หลายช่วงเข้าชม/ข้ามคืนแบบไม่ซ้อน, แยก `UNKNOWN` เมื่อแหล่งเวลาเปิดไม่พอ ทดสอบเป็น pure functions ก่อนเชื่อม Evaluation
3. **Weather:** เพิ่มการดึง Open-Meteo `hourly` ใน path แยก, ตรวจหน่วยและเวลาของ `precipitation`, `wind_gusts_10m`, `weather_code`, forecast window, cache และ provider failure; เก็บ coverage/provenance สำหรับต้นทาง ระหว่างทาง และปลายทางโดยยังไม่แปลงเป็น `L` หรือคะแนน
4. **Integration gate:** ทดสอบข้อมูล provider จริงแบบจำกัดคำขอ, ความตรงของเวลา/พิกัด และ V1 regression ก่อนเสนองาน Scoring ถัดไป ไม่มี UI/Chatbot, ไม่มีการเปลี่ยนสูตร V1 หรือการเขียนผล V2 ลง Trip Evaluation ในขั้น infrastructure
